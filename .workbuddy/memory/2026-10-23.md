**新增文件**
| 文件 | 作用 |
|---|---|
| `cloudfunctions/nexusImage/` | 派发侧：写 `ai_image_tasks`（`engine:'nexus'`）+ 不 await 触发 worker + 秒回 taskId；`action:'status'` 查状态 |

**关键决策**
1. **两段式**：`quality:'low'` 实测 33-36s，`high` 更慢，必然越过 `callFunction` 的 60s 客户端上限 → 和 Agnes 同一套「提交 + 轮询」，共用 `ai_image_tasks`。
2. **不要照抄 C# 的 `background:'white'`**：那是角色三视图用途，照片修图会被强制白底。
3. **图生图走 JSON 不是 multipart**：`images:[{image_url:'data:image/jpeg;base64,...'}]`，必须是对象数组。
4. **必须带浏览器 UA**（Cloudflare 1010），取图下载也要带。
5. 垫图统一转 base64 data URI（临时链接让网关回源失败只会回笼统 400）；合计 >15MB 直接报错防内存打满。

**尺寸（用户两轮强调「必须保持原图比例，不能固定 1024」）**
- 一开始按「探测网关行为」做的：传 880x1168 实出 1088x1445、传 1024x1024 实出 1254x1254 —— 说明网关按 ~1.57MP 归一像素但**保留比例**。
- 用户指出应该看官方文档，查 `developers.openai.com/api/docs/guides/image-generation` 拿到 gpt-image-2 的真实规则：
  - `size` 支持任意 `WIDTHxHEIGHT`（不是只有三档）
  - **两边必须都是 16 的倍数**（不是 8）
  - 长短边比 ≤ **3:1**
  - 总像素 655,360 ~ 8,294,400，最大边 ≤ 3840
  - 超过 2560x1440（2K）属实验性
- 据此写了 `pickNexusSize`（客户端）与 `fitOfficialSize`（worker 侧兜底校验），目标预算 1536x1024 ≈1.57MP。
- 对齐取整会把比例顶过 3:1（2176x720 = 3.02），补了一道「往上取整收口」→ 2176x736 = 2.96。

## 14:13 留言板实时刷新（原来没有，现已补上）

**结论**：原实现只有「进页面拉一次 + 下拉刷新 + 上滑翻页」，别人发的新留言不会自动出现 —— 确实没有实时刷新。

**方案：watch（真推送）+ 12s 增量轮询（兜底）双通道**
- 云函数 `list` 新增 `since`（毫秒）参数：`where({createdAt: _.gt(since)})`，只回新于它的留言，`limit` 放宽到一页上限、`hasMore` 恒 false；顺带在返回里加 `myOpenid`，客户端判断 watch 推送的文档是不是自己的（免得额外查一次）。
- 页面 `pages/leaveMessage`：
  - `startSync()` = `startPolling()` + `startWatch()`；`onShow` 恢复、`onHide`/`onUnload` 用 `stopSync()` 关掉（watch 会 close，`clearInterval`）。

## 15:44 调研：小程序能否做人脸识别

- 结论见 MEMORY.md 新增小节。要点：微信原生 `wx.startFacialRecognitionVerify` 存在且免费，但**必须非个人主体 + 类目对口 + 后台申请**，个人主体直接无入口。
- 自建方案（camera 取帧 + 服务端比对）技术上可行但没有权威库、活体不可靠，且《人脸识别技术应用安全管理办法》限制「人脸信息不得经互联网对外传输」「不得作为唯一验证方式」，风险大。
- 本项目判断：不做自建人脸；若将来要核身，先确认主体类型和类目再申请微信原生能力。
