## 修复微信开发者工具 MCP 接入报错 `-32000 Connection closed`

**现象**：`~/.workbuddy/mcp.json` 里 `wechat-devtools` 用 `"command": "wechatide"`，连接即断。

**根因（实测确认，四种启动方式对比）**：
| 方式 | 结果 |
|---|---|
| `spawn("wechatide")` | `ENOENT` —— 不在 PATH，MCP 客户端表现为 Connection closed |
| 直接 spawn `wechatide.cmd` | `EINVAL` —— Windows 不能直接执行 .cmd（无 shell） |
| `cmd.exe /c <绝对路径>\wechatide.cmd mcp --token ...` | ✅ initialize + tools/list 均通过 |
| electron exe + `-e` bootstrap + `ELECTRON_RUN_AS_NODE=1` | ✅ 也可行，备选 |

注意：PATH 里只有 `C:\Program Files (x86)\Tencent\微信web开发者工具\dll`，**根目录没进 PATH**，且有一个编码损坏的重复项（`???web?????????\dll`）。

**已改为**：
```json
"wechat-devtools": {
  "command": "cmd.exe",
  "args": ["/c", "C:\\Program Files (x86)\\Tencent\\微信web开发者工具\\wechatide.cmd", "mcp", "--token", "<TOKEN>"]
}
```
验证结果：`initialize OK -> mcp-server v0.1.0`，`tools/list -> 49 个工具`（automation_* / project_* / build_* / preview_* 等）。

**第二道坎**：Client 授权。新的 `clientInfo.name` 首次连接时，`initialize` 直接返回 `-32603 Client authorization pending`，需在开发者工具里点「允许」；授权后该 clientName 后续自动通过（实测 `probe` 已持久授权，换名即再次 pending）。所以 WorkBuddy 首次连上时必须有人盯着 IDE 的弹窗。

**Token 形式**：`--token=xxx` 与 `--token xxx` 都可用。MCP Token 与「CLI 访问令牌」是两套，去「设置 → 安全」点「复制 MCP 配置」才拿到正确的。

## 调研：云函数能否接 Agnes Image 2.5 Flash 生图

**结论：文生图可行，图生图不行（超时）。** 已用真 key 实测，非文档推断。

**接口事实**（实测）：
| 项 | 结果 |
|---|---|
| Endpoint | `POST https://api.agnes-ai.cn/v1/images/generations`，`Authorization: Bearer <key>` |
| 模型名 | `agnes-image-2.5-flash`（写成 `agnes-image-25-flash` → 404 `model_not_found`） |
| 文生图 1K | 8.7s / 10.3s |
| 文生图 4K 16:9 | 17.7s |
| 图生图（垫图，1K） | **85.4s / 95.7s** |
| 出图落点 | `cos-platform-outputs.agnes-ai.cn`（国内 COS，200 公开可读，非 googleapis） |
| base64 输出 | 1K 图 → 原始 887KB，JSON 1.18MB |
| 队列满 | 503 `生图队列已满，请稍后重试`（4 次图生图命中 2 次） |
| 无效 key | 401 `无效的令牌` |
| 异步任务查询 | 无。`/v1/images/tasks/*`、`/v1/tasks/*` 均 404 `Invalid URL` |

**云函数三个硬边界**：默认超时 3s；返回小程序数据 ≤1MB；出网**不受**小程序 request 域名白名单限制（这点是利好，无需备案/白名单）。

**⚠️ 重要修正（同日晚补测）**：`timeout` 60s 上限**只存在于微信开发者工具内置的云开发控制台**（那个输入框写死 1~60），**不是平台硬限制**。CloudBase 官方文档「云函数基础配置」明确：普通云函数（事件触发）超时可选范围 **1 秒 - 900 秒**，HTTP 云函数 1-7200 秒（实际控制台封顶 900）。改法：浏览器开 `https://tcb.cloud.tencent.com/dev#/scf?tab=function` → 切到当前环境 → 函数详情「配置」→ 改执行超时。**两边控制台配置共享，改完不用重新部署**。例外：最低档套餐的超时是「3s 且不支持修改」，需先确认套餐档位。

**三层超时要一起放开，缺一不可**：
| 层 | 默认 | 上限 |
|---|---|---|
| 小程序端 `wx.cloud.callFunction` 等待 | 60s（`app.json` → `networkTimeout.request`） | 建议设 600000 |
| 云函数执行超时 | 3s | 微信工具界面 60 / 腾讯云控制台 900 |
| 云函数内 HTTP 请求 | 代码自控 | 自设 |

**图生图耗时复测（补测，4 个样本）**：95.7s / 85.4s / 89.1s / 89.1s —— 稳定在 85–95s，属结构性慢，非拥堵（同一时刻文生图 8.6s，4/4 成功）。
**503 比例极高**：图生图累计 9 次调用中 6 次 `503 生图队列已满`，免费期队列严重拥堵。这个超时救不了，只能靠任务表 + 退避重试。

**轮询的定位（结论）**：轮询只能把「等待」从前端挪走，**不能延长执行体寿命**。云函数 60s 被杀时 HTTP 连接中断，Agnes 的响应永远到不了，URL 写不进库 → 轮询只能空转。所以顺序必须是：**先改超时 → 再上任务表轮询**，任务表的价值在于治 503 重试 + 前端不干等。

**「图片接口能否轮询」——已定论：不能。** 响应里那个 `task_id` 是追踪标识，不可查询，只在打日志/提工单时有用。证据链（2026-10-22 实测）：
| 证据 | 结果 |
|---|---|
| 图片文档里 `task_id`/`轮询`/`异步`/`poll`/`callback`/`回调` | **全部 0 次命中** |
| 图片文档出现的所有 `/v1/` 路径 | 只有 `/v1/images/generations` 一个 |
| 图片文档「请求超时」说明 | 「客户端超时时间建议设置为 **60s - 360s**」← 同步等待语义 |
| 视频文档（agnes-video-25） | `task_id` 12 次、`轮询` 6 次、`异步` 6 次，有 `queued/in_progress/completed/failed` 状态机 |
| FAQ 原文 | 「**视频任务**应按模型文档使用 `video_id` 轮询」← 只提视频 |
| `GET /agnesapi?task_id=<图片task>` | 400 `缺少 video_id` |
| `GET /agnesapi?video_id=<图片task>` | 404 `任务不存在` |
| `/v1/tasks/{id}`、`/v1/images/tasks/{id}`、`/v1/images/generations/{id}` | 404 `Invalid URL` |

**踩坑教训**：视频的轮询端点不是 RESTful 的 `/v1/xxx/tasks/{id}`，而是 **`GET /agnesapi?video_id=<ID>&model_name=agnes-video-2.5`**。第一次调研时按 RESTful 惯例猜路径，全部 404，差点误判成「连视频都不支持轮询」。以后探 Agnes 的查询接口要先看视频文档的真实路径形态。

**派生结论**：Agnes 只在**视频**上提供异步（`POST /v1/videos` 拿 `video_id` → `GET /agnesapi` 轮询）。**图片必须同步等**。所以 `agnesImage` 云函数的同步实现是唯一正确路线，不需要改。

**云托管额外优势**（CloudBase 官方原话）：云函数超时后强制中断；**云托管函数框架「支持函数调用超时控制，超时后函数代码可继续执行」**。要跑长任务云托管比云函数稳。

## 新增独立云函数 `cloudfunctions/agnesImage`

**独立实现，零依赖现有 `imageToImage`**（用户明确要求不碰后者，已确认 `imageToImage/` 未改动）。

**文件**：`index.js`（373 行）+ `package.json`（只依赖 `wx-server-sdk@4.0.2`）。**刻意不放 config.json 的 timeout 字段** —— 避免微信开发者工具部署时把控制台已改的 180s 覆盖回 60s。

**能力**：一个函数覆盖文生图 / 图生图 / 多图合成（靠入参是否带垫图自动判定）。垫图支持 `fileID`（云存储换临时链接）/ `imageUrls` / `images`（含 data URI），最多 4 张。

**关键设计**：
- **时间预算制**：`TOTAL_BUDGET_MS = 165s` 总预算，每次请求前算剩余，给下载+转存留 15s。避免「重试把预算烧光」。
- **重试只针对 503/5xx**，退避 4s→10s→20s。**网络超时不重试** —— 请求可能已进去并出图，重发等于白烧一次且必然再超时，交给用户手动再点更可控。401/404 直接抛，重试无意义。
- **200 但无 data** 单独处理：多半被风控或模型返回空，明确报「换个提示词重试」而不是含糊的 `HTTP 200`。
- `response_format` 必须放 `extra_body`，放顶层会被静默忽略（官方明确说明）。
- 转存失败不阻断，返回官方 url 兜底，额外给 `stored: boolean` 让前端判断。

**本地端到端验证**（用 `wx-server-sdk` 桩 + 真实 API）：
| 用例 | 结果 |
|---|---|
| 缺 prompt | `{ok:false,error:"请输入提示词"}` |
| 缺 AGNES_API_KEY（独立进程 `env -u`） | 正确报未配置 |
| `size:'abc'` | 回落到 `1K` |
| 文生图 1K | ✅ 7.7s / 8.5s，转存 868–1198KB 成功 |
| 图生图 | 503 重试链正常触发（4s→10s→20s，35–36s 后返回失败），但**当日队列持续满，未拿到函数内成功样本**；API 层 13:22 拿到过 89.1s 成功 |

**部署三步**（已写在文件头注释里）：① 控制台环境变量 `AGNES_API_KEY`；② 腾讯云 CloudBase 控制台把执行超时改 180s；③ `app.json` 加 `"networkTimeout": {"request": 180000}`，否则前端 60s 就断。

**注意**：每次重新上传部署后要复查超时是否仍为 180（微信工具界面只显示到 60，得去腾讯云控制台看）。

**14:36 复查修了三个缺陷**：
1. `cloud.init` 补上 `timeout: 150000` —— 原来没设，4K 图约 12MB 上传时可能撞 wx-server-sdk 默认超时（现有 `imageToImage` 就有这个设置，我第一版漏了）。
2. **429 纳入重试** —— 原来 `retryable` 只判 `503 || >=500`，而探测 `/agnesapi` 时实际收到过 `429 查询过于频繁`，生图接口同样会限流，原逻辑会直接判失败。现改为 `429 || 503 || >=500`。
3. `downloadImage` 加重定向深度上限 3 层，防环路无限递归。

修复后回归通过：`cloud.init` 带 timeout 生效，文生图 1K 8.3s 成功转存 955KB，非法 size 回落 1K，缺 prompt 正常拦截。

**代码完成度**：`index.js` 384 行 + `package.json`，功能层面完成。剩余是部署侧三件事（环境变量 / 改 180s 超时 / app.json networkTimeout），需用户操作。
**未闭环的一项**：图生图在云函数内的完整成功样本一直没拿到（当日队列持续 503），只在 API 协议层拿到过 89.1s 成功。部署后首次跑图生图要重点验这条。

**判定**：文生图 ✅ 同步走云函数；图生图 ❌ 85–95s 直接超 60s 上限，且无异步接口可轮询 → 只能改通道（CloudBase 云托管 / 前端直连 / 继续用混元 I2I）。base64 直返 ❌ 必须转存云存储返回 fileID（与现有 `imageToImage` 同一套做法）。

**待确认**：`cloudfunctions/imageToImage/` 目录里没有 `config.json`，超时到底配在哪（控制台还是默认）需核实，否则新函数照抄会踩 3s。

## 深挖：AI 出图提美（光影/人像/画质）

**产出**：`output/AI出图提美调研_光影人像画质.html`。

**核心结论（最反直觉、最有价值）**：AI 生成图变美的方向与传统修图**相反**。传统做加法（磨皮/提亮/加饱和），AI 图要做「减法+补偿」（压饱和、去过度平滑、补回毛孔颗粒不对称）。**给 AI 图加磨皮是负向操作。**
根因：训练集里精修商业人像在统计上也叫「真实照片」，所以 `realistic` 这个词无效。

**光影（三条路径）**：
- 生成时：光源实体 + 方位 + 高度差 + 硬软 + 色温，替代空泛的 "cinematic lighting"；只允许一个主光源；眼睛反光方向必须与主光一致；写环境反射。
- 重打光 IC-Light V2：6 向控制；**CFG 2.0–7.0（>8 生硬，严禁）**、Steps 20–25、提示词 ≤20 词、Highres Denoise 0.5–0.7。PS 回叠用**明度混合**只取光、柔光 60% 加强氛围、蒙版擦掉打错的地方。
- 后期调色顺序：降饱和 8–20 → 压高光提暗部 → 轻 S 曲线 → 颗粒 5–12 → LUT 30–60%。**只叠 LUT 会更假**，胶片感来自颗粒+色偏+非线性高光衰减。

**人像（对 AI 图要「丑化」）**：
- 正向词基础组：visible pores, natural skin texture, slightly oily T-zone, subtle under-eye texture；加强组按气质挑 1–2 个（freckles / acne scarring / uneven tone / redness around nose）。**2–3 个就够，堆多成「病历」。**
- 负面词是一半效果：no airbrushing / no beauty retouching / no plastic skin / no CGI skin / no doll-like skin / no perfect symmetry。
- 眼：虹膜纹理 + 角膜反射 + catchlight 方向与主光一致；脸：细微不对称（「细微」是关键）；发：单根发丝 + 碎发。
- **硬光比柔光更显纹理**（柔光等于暗示模型该磨皮了）。
- 后期救纹理只能靠频率分离：低频修颜色明暗、高频克隆真毛孔贴回。工具参考像素蛋糕（中性灰磨皮 + AI 网格 + 质感肌/奶油肌 + **AI 追色**样片对齐客片）。

**画质（保真 vs 创造，选错毁图）**：
- 保真派 SeedVR2 / Topaz Gigapixel 8 / Upscayl / PS 超分；创造派 Magnific / Krea / SUPIR / Nano Banana Pro。
- Everypixel 2026-08 盲评：SeedVR2 面部细节还原胜 Magnific **93% vs 0%**；整体细节 83.3%（真人）/87.9%（AI 图）。但 SeedVR2 紧脸裁切被评「蜥蜴皮」过锐；Topaz 在人像自然度反超（52% vs 14%），风景胜出。
- Magnific 会给包装加不存在的细节、脸塑料化、文字必崩、偏色 → **商品图/有文字画面禁用**。
- **必须先修缺陷再放大**（放大模型分不清真细节和 artifact）。
- 分阶段：1.5–2× 起步 → denoise 0.20–0.40 精修（要重生成纹理用 0.45–0.55）→ 局部 inpaint → 再 2× → 克制锐化。一步 4× 是错的。
- 1K→4K 耗时：SeedVR2 ~40s、Magnific Creative ~50s、Magnific 皮肤 ~60s、Nano Banana Pro ~80s、Topaz Image Enhance ~100s。
- 成本/1000 张：Upscayl $0、Topaz 买断 $99–199 无限、Magnific 标准档 ~$200。

**产品化建议（四按钮）**：①「去 AI 味」开关（颗粒+降饱和+色差）②「换光」6 向×3 氛围 ③「质感增强」不叫美颜 ④「整组统一/追色」。避免：磨皮滑块（对 AI 图负向）、在效果上收费。

**关键设计**：

- 多图时才往提示词里插参考说明（`第 1 张是要修改的原图，第 2 张起仅作为参考…`），位置在「保持不变」之前、约束行之前；单图不插，避免污染。
- 切引擎按新容量截断素材并显式提示（`已切到混元，只保留前 1 张图`），不静默丢图。

**踩坑（重要）**：`setData` 的 callback 是下一帧才跑，**派生字段不能放 callback 里算**——第一次实机测出 5 条断言失败（引擎切换后 outputLabel 还是旧值、删掉参考图后提示词仍带参考段），全是因为「先 setData 再在 callback 里 applyImages」。改成同步算完：`this.setData(patch); this.refreshPreview();`，并把 engine 显式传给 `applyImages(images, {engine, keepResult, error})`。

**踩坑（WXML）**：`{{index === 0 ? '主图' : '参考'}}` 在这套基础库上**不生效**（两个缩略图都渲染成"参考"，class 也没生效）。字符串比较 `stageView === 'src'` 是正常的，只有 wx:for 的 `index === 0` 出问题。结论：**wx:for 里别在模板做数值判断，标签在 JS 侧算好放进 item**（`item.label` / `item.isMain`）。

**验证**（三层）：
1. 单测（node 跑 .mjs）：20 条断言，尺寸/比例吸附/多图 payload/提示词顺序全过。
2. 云函数桩件测试（stub `wx-server-sdk` + 拦 `https`）：14 条，多图保序、超 4 张截断、单 fileID 兼容、换链接失败报错、imageUrls 优先、纯文生图不带 image。
3. 开发者工具实机（MCP 直连，沿用 `wechat-e2e.mjs` 的 RPC 骨架）：17 条断言全过，控制台无异常；截图确认混元/Agnes 两态都是一屏，无滚动。

## 线上实测结果（16:47–16:57）

**文生图 ✅**：11.7s 往返，云函数内 8402ms，`{ok:true, imageCount:0, stored:true, size:"1K"}`，落 `ai-images/agnes/1792658868292-scjwjg.png`。`imageCount` 字段存在 → 证明线上跑的是新代码。

**最关键发现（推翻旧认知）**：第 4 轮在 66s 报 `-501002 resource server timeout | ESOCKETTIMEDOUT`。
`wx.cloud.callFunction` **客户端硬限 60s，`app.json` 的 `networkTimeout.request=180000` 完全无效**（该配置只管 wx.request/uploadFile）。官方 CloudBase FAQ 原话：「建议控制函数执行时间，尽量不要把耗时长的操作放在客户端直接调用的云函数内……在云函数内使用 callback() 返回成功，客户端不等待执行结果，云函数会在超时时间内继续执行，把结果写入数据库，再在客户端获取」。
微信服务市场官方文章也写明「callFunction 默认限制云函数超时为 60 秒上限，无法通过腾讯云控制台修改突破」。juejin 复盘同样结论。

**所以**：光加 `networkTimeout` 和把云函数超时改 240s 都解决不了 Agnes 图生图（85-96s）。必须改成「派发函数立即回 taskId + 长任务函数不 await 调用 + 结果写 DB + 前端轮询」。文生图 8-10s 可以继续同步走。

## 修 dispatch 误判 + 验收通过（17:20–17:35）

**发现的真 bug**：验收时 4/6 轮在 **17s** 就被标成 `failed / 任务派发失败，请重试`，但任务其实还在跑。
根因：**云函数互调 `cloud.callFunction` 的 promise 约 15s 就返回失败**（不是 worker 结束），
派发侧 `.catch()` 里 `markFailed()` 直接把任务判死 → 用户 17s 看到失败，而图 90s 后才出（钱已经花了）。
更阴的是 worker 后会回写状态，导致事后查库看到的是 503，掩盖了误判。

**修法**：
- 派发侧 `.catch()` 只写 `dispatchError` 字段、**绝不改 status**；只有同步 throw（调用都没发出去）才 `markFailed`
- `status` 接口多返回 `dispatchError`
- 前端：`dispatchError && status==='queued' && 已等 > 60s` 才认定任务没起来（worker 一起来就写 running，不会误杀长任务）
- worker 退避从 `[4,10,20]s` 放宽到 `[4,8,15,25,40]s`（最多 6 次尝试，退避共 92s），守卫从「剩 40s」改成「剩 100s」——出一次图约 93s

**验收结果**：
| 项 | 结果 |
|---|---|
| 文生图（异步链路） | ✅ submit 538ms → running → 10s done，elapsed 9121，fileID 有 |
| 多图垫图（2 张） | ✅ 两次成功：elapsed 93462 / 93s 级，产物落在 `ai-images/agnes/`（1.5MB png） |
| 误判是否消除 | ✅ 修复后全程 running 到 93s，按真实 503 报错，不再 17s 假失败 |
| 503 队列满 | 仍高发：约 13 次尝试里成功 2 次（其余全是「生图队列已满」） |

**部署事实补充**：重新部署**不会**重置执行超时（两个函数部署后仍 240s），也没丢环境变量（部署后文生图直接成功）。

## 确认：混元出图右下角「由 AI 生成」水印不可关（22:30）

**结论：关不掉，只能改文案。**

- 底层混元生图 API（2.0/3.0/多轮对话）都有 `LogoAdd`，**默认 1**，右下角烙「图片由 AI 生成」；`LogoParam` 可换成自定义标识图。
- 我们走的是 `cloud.ai().createImageModel('hunyuan-image')`（CloudBase AI SDK）。官方《自定义水印》文档明确：SDK **只暴露 `footnote`**（水印文字内容），三种 SDK 均支持，服务端同步叠加、不额外耗时。
- CloudBase 社区 issue #1317 里腾讯云开发工程师正面回复：按法律要求 AI 生成内容必须有**显式水印 + 隐式水印**，SDK 不开放 `LogoParam:{LogoAdd:0}`，属产品决策，不是调参能绕过的。
- 法规依据：《人工智能生成合成内容标识办法》2025-09-01 施行 + 强制国标，生成端必须加显式标识，且不得恶意删除/篡改/隐匿。混元 FAQ 也只允许「使用默认标识或调整标识内容」。

**所以**：① 接受水印，或用 `footnote:'xxx'` 换成自家品牌文案（更有设计感）；② 裁切/模糊/覆盖水印属于篡改标识，不做，小程序上架也会核验标识能力；③ Agnes 出的图没这个水印（境外模型直连，不过国内标识链路），但「用哪个引擎」不该被当成规避标识的手段 —— 标识义务在小程序服务提供者身上。

**已实施（22:35）**：`cloudfunctions/imageToImage/index.js` 加 `WATERMARK_TEXT = '空谷'` 常量，`generateImage` 传 `footnote: WATERMARK_TEXT`。客户端不用改（`providers.js` 的 `buildPayload` 不涉及水印），无需重新发布小程序，只需重传 `imageToImage` 云函数。

**查证方式（可复用）**：本地没有 `node_modules`（云端装依赖），于是从 npm 拉三层层级包看实现 —— `wx-server-sdk@4.0.2` → `@cloudbase/node-sdk@3.17.2`（`dist/ai/index.js` 只做 createAI）→ `@cloudbase/ai@2.23.0`（`dist/cjs/models/image-model.js`）。结论：`generateImage` 就是 `this.req({url, data: input})`，**入参原样当请求体，无白名单**；`footnote` 在 `type.d.ts` 里有声明。

| 参考图 | `subject_reference: [{ type:'character', image_file }]`，`image_file` 收 URL 或 `data:image/...;base64,` |
| **参考图数量** | **每次只支持 1 张**（文档原话「当前每次请求仅支持传入一张参考图」），`type` 只有 `character`（人物主体参考） |
| 尺寸 | `aspect_ratio` 枚举 1:1/16:9/4:3/3:2/2:3/3:4/9:16/21:9；`width/height` 仅 image-01 生效但被 aspect_ratio 覆盖 |
| prompt | **硬限 1500 字符**（Agnes 是 2000） |
| 出图 | 同步返回，`data.image_urls`（24h 过期）或 `data.image_base64` |
| 业务错误 | **HTTP 200 + `base_resp.status_code`**：1002 限流、1004/2049 鉴权、1008 余额、1026 敏感词、2013 参数异常 |

**新增文件**：`cloudfunctions/minimaxImage/`（派发）+ `cloudfunctions/minimaxImageWorker/`（执行），与 Agnes 两段式完全同构，共用 `ai_image_tasks` 集合（任务文档多写 `engine:'minimax'`）。

**与 Agnes 的四处代码差异**：
1. 垫图转 **base64 data URI**（`cloud.downloadFile` → `data:image/...;base64,`），不是临时 URL —— MiniMax 回源拉不到只会回笼统的 `2013 参数异常`，排查成本极高；只有 1 张，体积可控。
2. 只看 HTTP 状态码不够，`readResult()` 把 `base_resp.status_code` 翻成「成功/可重试/直接失败」三态。
3. 重试面 = 1002 限流 + 429 + 5xx，退避 3/6/12/20/30s（累计 71s）；预算 150s、单请求 110s。
4. `prompt_optimizer: false` —— 本项目提示词是四段拼装，服务端改写会把「保持不变」的约束冲掉。

**前端改动**（`pages/aiImage/`）：
| 文件 | 改动 |
|---|---|
| `providers.js` | 新增 `sizeMode:'ratio'` 类型；`AGNES_RATIOS`→`RATIOS`（两者枚举恰好相同）、`pickAgnesRatio`→`pickRatio`（保留旧名导出）；`referenceHint(engine,…)` 改为按 `maxImages>1` 判断，不再硬编码 `'agnes'`；`buildPayload` 按 `sizeMode` 分派，彻底去掉 `engine.id` 判断 |
| `index.js` | 只改了 import 与两处调用（`pickRatio` / `referenceHint(engine,…)`） |
| `index.wxml` + `.less` | 引擎胶囊从「名字+副标题」改成**只摆名字**，说明挪到下一行右对齐 `{{engine.desc}} · {{engine.tip}}`；`.engine` 改 column，`.engine__item` 三等分 —— 3 个引擎并排原布局会把第三个挤掉 |
| `errors.js` | 新增两条：余额/额度（不可重试）、敏感词审核（可重试），都排在「队列满」之前 |

**MiniMax 的 `maxImages` 定成 1（不是 4）**：subject_reference 只收 1 张，给对方 4 个槽位却只偷偷用第 1 张属于误导。所以它走单图 UI（同混元），但流程走 Agnes 的「提交+轮询」。

## MiniMax 真机测试（23:20–23:30）—— 卡在超时未改

**实测**：`submit` 686ms 回 `taskId: 080954836ada29cc00055f0a51bae44c`（派发侧 3s 超时够用），随后任务文档只到 `status:'running'`（写入时刻 = 创建后 4.2s），**25s 后再查仍是 running，`updatedAt` 不再变** → worker 被函数执行超时杀掉，catch 里那句 `patchTask(failed)` 没机会执行。

**关键推断：API Key 是配了的。** worker 的 `patchTask(running)` 在 `if (!API_KEY) throw` **之前**，所以 running 本身不证明有 key；但若是缺 key，会在 ~1ms 内抛错并写 `failed` —— 实际没有，说明它忙着下载垫图/调 MiniMax 时被杀。同理"卡 running 不写 failed"就是"函数被超时杀"的特征信号。

**复查**：`cloud_fn_info` 两个函数 timeout 仍都是 **3s**（用户说"都配置了"= 配了环境变量，超时没改）。

**顺带确认**：`dispatchError:"任务派发异常"` 照旧出现（云函数互调 promise ~15s 抛错），不是新问题；派发侧 3s 也能顶住（686ms）。

**测试用垫图**：`cloud://cloud1-d4g48z822d1300a77.636c-cloud1-d4g48z822d1300a77-1512321434/ai-images/input/1792680989554-8nzwodqm.jpg`（346KB 人像）。
**fileID 桶前缀怎么拿**：`ai_image_tasks` 里任一 done 任务的 `fileID` 就是 `cloud://<env>.<bucket>-<uin>/...`，把后面的路径换成 `ai-images/input/<key>` 即可拼出任意已上传图片的 fileID（`cloud_query_storage list` 只给 Key，不给 fileID）。
