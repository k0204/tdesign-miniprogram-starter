**关键设计结论（重要）**：图生图提示词与文生图逻辑不同——文生图是"描述一张图"，图生图是"给一张图下修改指令"。因此所有 prompt 统一写成**祈使句**（"把背景换成…"、"改为伦勃朗光…"），并在最前面固定加 `保持原图主体的五官、表情、姿态和服装不变`。中文提示词靠前的约束权重更高，所以拼装顺序固定为「不变项 → 自定义 → 背景 → 灯光 → 风格」。

**专业术语依据**（已核对中文摄影资料，非臆造）：经典五光位为伦勃朗光（暗侧倒三角光斑，1:4~1:8）、蝴蝶光/派拉蒙（鼻下对称蝴蝶影）、环形光（环形影不与面颊阴影相连）、分割光（90 度，明暗各半）、平光；另加宽光/窄光（影响脸型胖瘦）。三点布光＝主光45度+辅光1/2~1/4强度+轮廓光。光质分硬光/软光，附件含柔光箱/八角箱/雷达罩/蜂巢/束光筒/裸灯/环形灯。自然光时段＝黄金时刻（日落前1h，3000-5000K）、蓝调时刻、阴天漫射、窗光。背景体系＝无缝纸（Savage/Colorama，最平整）、丝绒（吸光）、渐变、无影墙/Cyc、纹理、实景环境、自然。

**尚未接入**：页面 UI 仍是原来 5 个硬编码预设词，未消费该数据模块。用户明确说"先只调研"，接入待确认。

## 原图上传前压缩（同日）

用户问"能否不上传云存储直接下载"，调研后结论：**输入侧可省、输出侧不可省**，最终只做输入侧优化。

**改法**：`pages/aiImage/index.js` 新增 `compressSource()` + `prepareSource()`；`chooseImage` 的 `sizeType` 由 `compressed` 改为 **`original`**（自己压一次，避免微信先压再压的双重有损）。删掉旧 `uploadSource()`，改为 `uploadToCloud()` 只负责上传并返回 fileID。
- `MAX_LONG_SIDE = 1600`（低于 1024 丢五官细节，高于 2000 徒增体积）
- `SKIP_COMPRESS_SIZE = 300KB`，小于此值不处理
- 只传 `compressedWidth` 或 `compressedHeight` 中的一个（按长边），让微信等比缩放，避免宽高都传时四舍五入导致拉伸
- 任何一步失败都 `resolve(src)` 回落原图，不阻断
- `removeImage` 增加 `uploading` 守卫，防止上传中途清空导致状态错乱

**已核实的硬限制（官方文档，别再试错）**：
1. `wx.compressImage` 的 `compressedWidth/Height` 需 **基础库 2.26.0+**；且 **iOS 仅支持压缩 JPG**，PNG 会走 fail（已做回落）
2. `wx.getImageInfo` 原文档明确"网络图片需先配置 download 域名才能生效"；`wx.saveImageToPhotosAlbum` **只收本地路径，不支持网络图**。所以输出侧放弃云存储代价极大（需配 downloadFile 白名单 + 官方 URL 24h 失效），保持转存 `fileID` 不动
3. `wx.cloud.callFunction` 的 `data` 上限 **5MB**（云函数同步请求上限 6MB）

## 改为 base64 直传（同日，用户最终决定）

用户明确要求"直接 base64"，推翻上面的 uploadFile 方案。**原图不再落云存储**。

**`pages/aiImage/index.js`**：
- 删除 `uploadToCloud()` 与 `randomName()`（不再 uploadFile）
- 新增 `readAsBase64()`：`wx.getFileSystemManager().readFileSync(filePath, 'base64')`
- data 拆分：`sourcePath`（仅预览）/ `sourceBase64`（选图产生的真正入参）/ `sourceFileID`（仅"继续修改"继承上一轮结果）
- `generate()` 分支：有 `sourceFileID` 传 `fileID`，否则传 `images: [sourceBase64]`
- 新增 `MAX_PAYLOAD = 4MB` 客户端闸门（data 上限 5MB，留 1MB 给 prompt 与协议开销），超限直接给「图片过大」提示，避免传输层报错难懂

**「继续修改」不走 base64**：直接把上一轮结果的 `resultFileID` 继承为 `sourceFileID`，省掉一次下载+编码。

**收益**：`ai-images/input/` 不再堆积垫图，之前那个"没人清理"的问题自动消失。

**代价**：每次调用多传约 1.33 倍字节；base64 无法携带 MIME 提示，PNG 在 iOS 上因 `compressImage` 不支持而不会被压缩，会更加重这条路径（观察点）。

## 改为「base64 优先 + 超限回落云存储」（同日，最终形态）

用户追加要求：base64 超体积就走云存储。已实现无感分流。

`pages/aiImage/index.js` 的 `prepareSource()` 现在是三分支：
1. 压缩 → `readAsBase64()`
2. `base64 && base64.length <= MAX_INLINE_BASE64(3.5MB)` → 用 `images: [base64]`
3. 否则（超限 **或** 读取失败返回空串）→ `uploadToCloud()` 拿 fileID，用 `fileID`

`generate()` 只按 `sourceFileID ? {fileID} : {images:[base64]}` 分支，不需要再判断体积。
**注意**：原先 generate 里的 `MAX_PAYLOAD` 前置拦截已删除（会变成未定义变量引用），改由 `prepareSource` 收口——体积判定只在一处，避免两套阈值不一致。

## 【重要】callFunction 入参真实上限 ≈ 1MB（同日踩坑）

实测报错：`cloud.callFunction: fail error data exceed max size`。

**关键纠正**：CloudBase 文档写的「data 上限 5MB」是**云端**限制，微信端 SDK 实际卡在**约 1MB**。多篇实践记录一致（"约1MB"/"通常是1MB"）。另 `docs.cloudbase.net/error-code/EXCEED_MAX_PAYLOAD_SIZE` 说「文本类型请求体 100KB、其他 6MB」，那是 **HTTP 触发器**的限制，不是 SDK callFunction，别套用。

**修复（两层）**：
1. `MAX_INLINE_BASE64` 由 3.5MB 改为 **700KB**（留余量）
2. 新增 `callGenerate()` 运行时兜底：捕获错误文案匹配 `PAYLOAD_TOO_LARGE`（`/exceed max size|max size|payload.*(too|exceed)/i`）时，用 `this.data.sourcePath` 上传云存储 → 写入 `sourceFileID` → 用 fileID 重试一次。仅对超限错误重试，避免重复消耗生图额度。

**经验**：客户端体积阈值只能当"估算"，真实上限随基础库变化；凡是靠阈值分流的地方，都必须配一个「按错误文案重试」的兜底，否则用户会看到底层报错。

**可选升级**：微信云开发提供 `wx.cloud.CDN(大字段)`，自动把大数据上传到临时 CDN，云函数端收到的是 URL（可直接当 `image_urls` 用，连下载都省了）。建议临界值 256KB。若以后要彻底摆脱云存储且不受 1MB 限制，走这条。

## 修复出图比例恒为 1:1（同日）

**根因**：调 `generateImage` 时**没传 `size`**，模型默认 `1024x1024`。

**官方文档核实结论**（`docs.cloudbase.net/api-reference/server/node-sdk/ai`）：
- `size` 格式 `"宽x高"`，默认 `"1024x1024"`
- 宽高各自范围 **[512, 2048]**，**面积不超过 1024×1024**
- **支持自定义宽高比**，没有 `aspect_ratio` 参数，比例只能靠 size 表达
- 注意：文档示例里的 `ALLOWED_SIZES`（1024x1024/1280x720/720x1280/1280x1280）只是**示例代码的校验白名单**，不是真实枚举，别当限制

**实现**：
- 前端 `pickSize(w,h)`：`w = sqrt(MAX_AREA * ratio)` 反解，比例夹在 [0.25, 4]，**向下取整到 8 的倍数**
  - 踩坑：最初用 `Math.round` 对齐 16，4:3 会算成 1184x896 = 1060864 **顶破面积上限**，且再缩放会四舍五入回去，必须用 `Math.floor`
- 实测映射：4:3→1176x880、3:4→880x1168、16:9→1360x760、9:16→768x1360、1:1→1024x1024、3:2→1248x824、6:1→2048x512（比例夹到 4:1）
- 前端 `readImageInfo()` 用 `wx.getImageInfo`（本地路径，无需域名白名单）取宽高，`sourceSize` 存 data 并在 UI 显示「输出尺寸」
- 云函数 `normalizeSize()` 二次校验：不匹配 `^\d{3,4}x\d{3,4}$` 或越界 → 回落 `1024x1024`
- `useAsSource()` 不变（结果已是正确比例）；`removeImage()` 重置为默认
