结论先说：把「模板」理解成一张设计稿是错的，它应该是一份可被程序消费的规则数据（JSON）。 同一份数据在三个环节复用——生成时约束构图、合成时决定字号与坐标、审图时变成 16 条可打分的检查项。 这样模板不是装饰，而是可量化、可回归、可 A/B 的产品资产。

01两个平台到底差在哪：一个靠「文字被搜到」，一个靠「文字被扫到」

这是整套方案的前提。抖音和小红书的封面都在加字，但文字承担的任务完全不同， 照抄一套参数必定翻车。

维度小红书抖音

由此得到一个直接的产品判断：小红书模板必须"文字能被 OCR 读出来并成为关键词"，所以字号下限、对比度是硬指标；抖音模板必须"缩略图状态下 3 米外能认出"，所以字数上限和字重是硬指标。两套阈值不能共用一个。

02文案：四个可套用的公式，和一次「压缩三步法」

封面文案不是写出来的，是从正文里压缩出来的。这是整个环节最值钱的动作，也最适合做成模板槽位。

压缩三步法

STEP 1

找结果
用户最关心的变化：变白、变瘦、省钱、省时间、少踩坑。

STEP 2

加具体
塞进一个数字或场景：3 天 / 5 款 / 155cm / 出租屋 / 通勤。

STEP 3

造反差
对比、反问、否定常识："别买了""原来不用花这个钱"。

四个封面标题公式（附改造示例）

公式 1 · 数字清单型 ＝ 数字 + 核心词 + 结果承诺
分享一下我最近在用的面霜 → 3 款平价面霜，敏感肌褪红实测
公式 2 · 痛点提问型 ＝ 痛点场景 + 解决方案暗示
关于油皮定妆的一些经验 → 油皮夏天脱妆到崩溃？这手法持妆 12 小时
公式 3 · 对比反转型 ＝ 常识 vs 真相 / Before vs After
装修预算怎么省 → 花 1000 块买面霜，不如这 100 块的
公式 4 · 身份锁定型 ＝ 身份标签 + 具体场景 + 方案
备菜方法分享 → 上班族妈妈｜每天 10 分钟搞定早晚饭

实测数据显示：同时具备痛点共鸣与数字量化的标题，点击率平均高出 30%–50%；同一款产品，把「优质猫粮推荐」（CTR 6.8%）改成「养猫 3 年换了 10 种猫粮，终于找到这款不软便的」（CTR 23.5%），点击率提升 245%。

正文结构（决定完读与收藏）

段落该写什么硬约束
开头直接抛结论或最强卖点，含核心关键词≤ 80 字，前 5 字含核心词
中段分 3 点展开，每点配一张图；用 1️⃣2️⃣3️⃣ 或 ✅❌ 做路标每段 ≤ 3 行（40–60 字），段间空行
结尾引导收藏或提问：「收藏这篇对照买」1 句，不要「求关注」
标签3–5 个精准语义标签，品牌词放前 3 位不堆 10 个泛流量标签

03加字：一套可换算的层级，和五条绝对不能碰的禁区

字号不要用绝对 px 交付，要用画布宽度的百分比。这样 1080×1440 和 1242×1656 共用一套模板， 换画布只换乘数，不用重做设计。

可读性红线：等效字号低于 40px（＜3.7% 画布宽）在信息流缩略图状态不可读，直接判不合格。

压图必须加的两件事

  • 描边：白字压任何照片，加 8–12px 黑描边（不透明度 0.35）
  • 投影：y 偏移 0.8%H，模糊 2%H，黑 28%
  • 或改用底部渐变蒙层（0.58H → 0.95H，黑 65%）

五条禁区

  • 手写体 / 艺术字叠加，缩略图必糊
  • 细衬线小字直接压照片
  • 单行超过 12 字
  • 文字距边 < 5% 宽
  • 全大写英文长串（中文场景无识别效率）

05模板做成什么：三个层次，一份数据，三处复用

这是整个方案的核心设计。模板不是一张 PNG 底图，而是三个可解耦的层：

LAYER 1

骨架 Skeleton

图片区、色块区、蒙层的归一化坐标（0–1）。决定"图在哪、字在哪"，不含任何具体文字。

LAYER 2

样式令牌 Type Tokens

字号/字重/行距/描边/配色，全部相对画布宽高。换画布只换乘数。

LAYER 3

文案槽位 Slots

每个槽位声明角色、最大字数、行数、是否必填。AI 填槽，不负责排版。

06塞进 AI 审图：从「审合规」变成「审模板符合度」

现有链路里的「审」只有合规一层（微信 media_check_async + 回调兜底）， 它只回答"能不能发"，不回答"发了有没有人看"。新增模板审，本质是把 运营经验翻译成可计算的检查项。

L1
合规审（已有，不动）
微信内容安全 / 敏感词 / 版权。答案：能不能发。
L2
质量审（新增，与技术指标相关）
分辨率、是否糊、人脸是否变形、文字是否被裁、水印是否合规。答案：这张图是不是废片。
L3
模板审（本次新增，与分发效果相关）
按选中模板的规则集逐项校验并打分。答案：这张图发出去能不能被点。

16 条规则，全部可计算

每条规则都有明确的计算方法，不依赖大模型的主观判断——这样才能做回归测试和阈值调优。权重合计 100。

评分与三个硬性拦截

分档

  • 90+　A　可直接发布（pass）
  • 75–89　B　微调后发布（suggest）
  • 60–74　C　需重排（rebuild）
  • <60　D　建议重做（regenerate）

硬拦截（任一失败，总分封顶 59）

  • C1 画幅比例 — 平台侧直接损失占屏
  • S1 安全区 — 关键文字会被 UI 压住
  • T2 对比度 — 文字实际不可读

这三条不是"扣分项"，是"发出去就是废图"，必须先修。

审图输出的不是分数，是「可执行修改」

每条 finding 必须绑定一个可自动执行的 fix 动作，用户点一下就能改，而不是给一段文字建议。

{
  "templateId": "T2-top-text-bottom-image",
  "platform": "xhs",
  "score": 62, "band": "C 需重排",
  "dims": { "画幅":10, "安全区":8, "文字可读":17, "版式":9, "配色":12, "文案":6 },
  "findings": [
    { "ruleId":"S1-safe-zone", "level":"blocker",
      "detail":"标题下沿 y=0.925H，越出底部安全线 0.92H",
      "fix":"整体上移 1.5%H 或缩到 1 行", "action":"raise-title" },
    { "ruleId":"T2-contrast", "level":"blocker",
      "detail":"白字压浅米色图，对比度 2.1:1",
      "fix":"加 10px 黑描边，或把标题移到色块区", "action":"add-stroke" },
    { "ruleId":"W1-copy-pattern", "level":"warn",
      "detail":"「夏日穿搭分享」未命中数字/人群/痛点",

注意最后一条：文案类问题必须由模板的槽位约束反推出修改。 因为 maxChars: 9 已声明在槽位上，AI 改写时就能保证"改完不超字数、不超行数"， 不会出现"建议很好但塞不进去"的尴尬。

07工程落地：一个必须先说的坑

不要在服务端用 sharp 渲中文文字

现有 watermark.js 用 sharp 烧「AI 生成」角标是可行的（纯 ASCII + 简单图形）， 但 sharp 的文字走 librsvg，依赖系统 fontconfig。Linux 容器缺中文字体时输出空白， Windows 下更容易出现字宽错乱、标点错位。用它做模板排版会得到"线上好好的、换台机器全乱"的经典故障。

正确分工：

环节技术选型理由
模板合成小程序端 canvas 2d（类型 2d，非旧版）字体跟随系统、所见即所得、文案可实时拖动改，无需服务端往返
字体策略系统字（苹方/思源黑体）+ 关键模板内嵌一份 woff2 子集1080 宽下系统字已够；仅当需要固定字形时才内嵌，避免包体膨胀
OCR腾讯云文字识别（已在微信生态内，无需新增合规面）输出带坐标的文本框，正好是规则计算需要的输入
颜色分析sharp 缩放到 64×64 → k-means k=5纯像素统计，与文字无关，服务端做最省
人脸/主体框微信侧已有能力或轻量检测模型只用于 S2 遮挡判定，精度要求低

接入位置建议：watermark.js 之后、入库之前加一道 templateReview。此时图已带 AI 标识，审的是最终交付物。

// src/services/templateReview.js  （伪代码）
async function review(filePath, { templateId, platform }) {
  const tpl  = loadTemplate(templateId);          // 读 JSON
  const meta = await sharp(filePath).metadata();   // C1 / C2
  const ocr  = await ocrBoxes(filePath);          // 带坐标的文本框
  const pal  = await dominantColors(filePath, 5);  // P1 / P2 / P3

  const hits = tpl.ruleset.map(r => r.evaluate({ meta, ocr, pal, tpl, platform }));
  const score = clamp(100 - sum(hits.filter(h => !h.pass).map(h => h.weight)));
  return {
    score: hasBlocker(hits) ? Math.min(score, 59) : score,
    band: toBand(score),
    findings: hits.filter(h => !h.pass).map(toFinding),
    applyableFixes: hits.map(h => h.action).filter(Boolean)
  };
}

1. 模板是用户选还是系统推荐？建议按内容类型自动给 2 个候选，用户只做减法——选型成本是这类功能最大的流失点。
2. 审图何时触发？建议生成后立即跑，但 UI 上做成"建议"而非"拦截"，只有三个 blocker 才拦。
3. 模板的归属：官方模板与账号私有模板要分表，否则后面做"账号视觉资产"会推倒重来。
