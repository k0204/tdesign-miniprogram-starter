# 参考图提示词检索方案 v1

> 目标：用户给一张图（可选一句白话需求），返回 4 个「最匹配」的提示词方案。
> 前提：**不能把 2253 条提示词全丢给 DeepSeek**，必须先检索收敛。
> 本文只做方案分析，不含代码实现。

---

## 0. 结论先行

| 问题 | 结论 |
|---|---|
| docs 里有多少可用语料 | **2253 条**（A 库 1450 + B 库 803），去重后无重复编号；16 个文件里有 6 个是重复呈现或过程日志 |
| 需要几层结构 | **5 层**：词表 / 条目索引 / 风格簇 / 规则 / 产品配置 |
| 检索用什么 | **结构化加权匹配（倒排 + 维内相似度）**，不需要向量、不需要 embedding |
| 云函数够不够 | **够，且余量 27 倍**。索引 181KB、单次检索 3-6ms、内存 ~6MB |
| 要不要检索 server | **不要**。当前 2253 条一条触发条件都不满足（见 §6.3） |
| 和现有 DeepSeek 分析怎么接 | 把「一次自由发挥」改成「先拆标签 → 查库 → few-shot 注入 → 生成」，**函数名、出参、前端全不用改** |
| 最大风险 | 两库「风格」字段同名不同义（A 是题材、B 是流派），直接合并会污染检索；另有 6 处数据缺陷必须先修 |

## 2. 五层分类结构

```
L0  schema.json      34 字段 × 2344 个封闭取值 + 同义映射 + 维内相似度表   34 KB
      ↓ 决定「怎么比」
L1  index.json       2253 条 × 33 维，列式 + 枚举 ID 编码               181 KB
      ↓ 决定「和谁比」
L2  clusters.json    ~15 个风格簇（22 簇去重合并）+ 每簇骨架 + 代表条目
      ↓ 决定「选项要不要分化」
L3  rules.json       权重表 + 渲染规则 + 固定尾缀 + 反向提示词
      ↑ 决定「怎么拼出来」
L4  产品配置          beauty-presets / copy-library / share-templates（与本检索无关）
L5  调研文档          三份 html，只作决策依据，不参与运行时
```

**分层的意义**：L0/L3 是「知识」，改一次全库受益；L1 是「数据」，只增不改编；L2 是「聚类结果」，随 L1 重算。三者生命周期不同，混在一个 csv 里就会互相牵制。

## 3. 七个必须先修的数据缺陷

这些不是洁癖，是**会让检索结果直接错**的问题。

### 3.1 「风格」字段同名不同义（最严重）

| 库 | 取值 | 实际语义 |
|---|---|---|
| A（1450） | 女性肖像摄影 183 / 儿童人像摄影 137 / 情侣婚礼摄影 113 | **题材**（拍的是谁） |
| B（803） | 日系胶片人像 61 / 古风国风人像 62 / 复古港风人像 62 | **流派**（拍成什么样） |

后果：用户说「日系」，A 库 25 个取值里 0 命中，B 库命中 61 条 → 结果全来自 B 库，A 库 1450 条等于废掉。

**处置**：拆成两个正交字段 `题材`（人物类型）与 `流派`（视觉风格）。A 库 25 值全部重映射为题材；流派按 §3.6 的方式从 `后期质感 + 色调 + 光线性质` 推断补全。

### 3.2 情绪维度塌陷

| 库 | 最高频值 | 占比 |
|---|---|---|
| A | 自然真实 | 527 / 1450 = **36%** |
| B | 自然真实 | 702 / 803 = **87%** |

后果：B 库 87% 的条目在情绪维上完全相同，这一维等于一个常数。权重给高只会让所有候选同分。

**处置**：权重压到 0.04，且把「自然真实」当**缺失值**处理（不参与分母）。

### 3.3 前景维度 B 库 100% 空

`images-analysis.csv` 的 `前景遮挡` 列 803 条全是 `—`。

后果：若空值按 0 分算，任何带前景条件的查询都会把 B 库整库淘汰。

**处置**：**逐维缺测跳过** —— 只对「查询和候选都有值」的维度计入分母。这是打分公式必须写成比值而不是和值的原因（见 §5.2）。

### 3.4 构图字段粒度不一致

- A：拆成 `构图手法(5) / 景别(4) / 景深(3) / 画幅(3)` 四个正交维
- B：`构图手法(53)` 是复合串 —— `环境人像构图，主体居中，大景深，环境清晰，竖幅构图`

后果：B 的 53 个取值几乎两两不等，跨库比较时相似度恒为 0。

**处置**：B 库按 4 个正交维拆解（已能机械拆，逗号分隔 + 模式匹配），拆不出的置 null。

### 3.5 景别命名体系冲突

| A | B |
|---|---|
| 环境人像构图 / 半身构图 / 面部特写 / 七分身与全身构图 | 大场景构图 / 俯瞰大场景 / 长焦局部构图 / 中近景，背景虚化 |

**处置**：统一映射到 `远景 / 全景 / 中景 / 近景 / 特写`（A 库「环境人像构图」→ 全景，「七分身与全身」→ 全景，「半身」→ 中景），原词保留在 `display` 字段供渲染用。

### 3.6 光线方向疑似系统性误标

A 库 `底光` 120 条（8.3%）—— 人像摄影里底光极为罕见，更可能是把「顶光下的下半脸提亮」或「室内地灯」误判。

**处置**：抽样 30 张复核；复核前该维权重从 0.16 降到 0.10。

### 3.7 反向提示词是全局常量

两库各只有 **1 个唯一值**（46 字，1450/1450 与 803/803 完全相同）。

**处置**：提到 L3 配置层，不占 2253 条记录的字段位。

> 附带：A 库 `场景类型` 1176/1450 = 81% 是 `—`，B 库该字段实际存的是「人物/场景」（这是类别不是场景）。**建议直接删除**，用 B 库 `类别`（01-人物 / 02-风景 / 03-街拍）作硬过滤维度。

## 4. 关键发现：提示词是「可再生的」

实测（脚本比对 A 库全部 1450 条）：

| 检查项 | 结果 |
|---|---|
| 提示词片段能在同行维度字段**精确命中** | 31526 / 40429 = **78.0%** |
| 未命中的片段是什么 | 100% 是渲染包装，无新信息 |
| 固定尾缀 `自然皮肤质感，真实细节，高清摄影` | **1450 / 1450 = 100%** |

未命中片段的全貌（前 200 条抽样）：

| 渲染规则 | 例子 |
|---|---|
| `机位` + 「以…拍摄」 | 「平视机位」→「以平视机位拍摄」199/200 |
| `表情` + 「神情」前缀 | 「自然平和」→「神情自然平和」105/200 |
| `环境` + 「置身于」前缀 | 「环境细节丰富的场景中」→「置身于环境细节丰富的场景中」114/200 |
| `天气时间` + 「氛围」后缀 | 「冬季」→「冬季氛围」6/200 |
| `道具` + 「手持」前缀 | 「相机」→「手持相机」5/200 |

**结论：`提示词 = 维度向量 × 渲染规则 + 3 条固定尾缀`，可 100% 机械再生。**

这带来三个直接收益：

1. **索引不存提示词**，体积从 1087 KB 降到 0；需要时现渲染。
2. **「换槽位」成为可能** —— 想把库里的配方套到用户自己的图上，只需替换 `主体/服装/场景/姿势/道具` 五个槽，保留 `机位/焦段/景别/景深/光线/构图/色调/后期/情绪` 九个风格槽。这是一次字符串替换，0 模型调用。
3. **候选可以按需改写长度** —— 同一个向量能渲染成 60 字短版或 180 字长版，不用重跑模型。

## 5. 检索架构

### 5.1 为什么不能全给 DeepSeek（四条硬理由）

| # | 理由 | 量化 |
|---|---|---|
| 1 | **装不下** | 2253 × 170 字 ≈ 38 万字 ≈ 50 万 token，DeepSeek 上下文 64K-128K |
| 2 | **注意力稀释** | 即使分片塞，50 万字里挑「最像」会退化成「挑几条看起来像的」，不可控且不可复现 |
| 3 | **成本与延迟** | 单次从 ¥0.003 涨到 ¥1+，延迟从 5s 涨到 60s+ |
| 4 | **无法排查** | 模型自由挑是黑盒；检索是确定性的，同一输入永远同一输出，出问题能定位到具体维度 |

### 5.2 三段链路

```
图片 ─┬─→ ① 视觉拆解（DeepSeek vision，1 次）
      │      输出：18 维标签向量，每维只能从封闭词表选，或 null
      ↓
   标签 ─→ ② 检索（纯本地，0 模型调用）
      │      硬过滤 → 加权匹配 → 多样性重排 → top-8（覆盖 4 个簇）
      ↓
  top-8 ─→ ③ 生成（2 选 1）
              快速模式：槽位替换 → 直接渲染 4 条（0 额外调用）
              增强模式：few-shot 注入 → DeepSeek 生成 4 条（1 次文本调用）
```

### 5.3 打分公式

```
score(x, q) = Σ_d [ w_d · sim_d(x_d, q_d) ]  /  Σ_d [ w_d · has_d(x, q) ]

  has_d(x,q) = 1  当且仅当 x_d ≠ null 且 q_d ≠ null
```

**为什么是比值而不是和值**：分母只算「两边都有值」的维度 → 缺测维度自动退出比较，不会因为空值拉低分数（解决 §3.3 的 B 库前景全空问题）。

`sim_d` 用**维内相似度表**，不是 0/1：

| 关系 | sim | 例子 |
|---|---|---|
| 完全一致 | 1.0 | 左侧光 ↔ 左侧光 |
| 同族 | 0.8 | 自然柔光 ↔ 均匀柔光 ↔ 高调柔光 |
| 相邻 / 镜像 | 0.5 | 左侧光 ↔ 右侧光；暖色温 ↔ 中性色温 |
| 相反 | 0.15 | 暖色调 ↔ 冷色调 |
| 无关 | 0 | 左侧光 ↔ 顶光 |

维度基数一共 2344 个取值串，但**真正需要人工定义相似度的只有 12 个核心维、约 120 个取值**，一张表半小时能写完。剩下 22 个低权重维用 0/1 即可。

### 5.4 权重表（初值）

| 维度 | 权重 | 依据 |
|---|---|---|
| 光线方向 | 0.16 → 复核后 0.10 | 6 值分布最均衡（345/332/265/204/184/120），区分度最高 |
| 光线性质 | 0.14 | 柔/硬是风格分水岭 |
| 后期质感 | 0.13 | 7 值，直接对应「胶片感 / 黑白 / 暗调」三大流派 |
| 色调 | 0.11 | 暖/冷/低饱和 |
| 景别 | 0.09 | |
| 构图手法 | 0.08 | |
| 流派（新增） | 0.08 | §3.1 拆出来的核心字段 |
| 色温 | 0.06 | |
| 情绪 | 0.04 | 塌陷（§3.2），压低 |
| 背景处理 | 0.04 | |
| 前景 | 0.03 | B 库全空 |
| 环境 | 0.02 | 52 值太自由 |
| **主体 / 服装 / 道具 / 姿势 / 表情** | **0** | **不参与相似度，只做槽位替换** |

**最后一行是整个设计最要紧的取舍**：

这四项描述的是「这张照片里有什么」，而检索要找的是「这张照片该怎么拍」。把它们计入相似度，会让「都是年轻女性」的图互相吸引，而不是「都是暖调胶片」—— 检索退化成内容匹配，风格层信息被淹没。

把它们降为**槽位**后，同一个「暖调胶片 + 左侧柔光 + 中心构图」的配方，可以分别套到「少年 / 海边 / 白衬衫」和「老人 / 室内 / 毛衣」上，产出两条完全不同的提示词。**这才是库的复用价值。**

### 5.5 用频次做排序修正

库的真正价值不是「哪一张最像」，而是「哪些维度组合在真实成片里反复成立」。

- 「平视 + 柔光 + 中心 + 暖调胶片」→ A 库 S01 簇 353 张（24.3%）
- 「俯拍 + 硬光 + 特写 + 冷调」→ 可能全库只有 2 张

如果纯按相似度排，长尾怪组合可能排到第一 —— 用户拿到一个「成立概率 0.1%」的配方。

**修正**：`final = score × (1 + 0.15 · log2(1 + clusterSize))`

簇大小不直接压分，只做温和加成。避免完全被高频簇吞掉（那会让 4 个候选全变成暖调胶片）。

### 5.6 多样性重排（决定「多个选项」是不是真的有区别）

4 个候选必须来自 **4 个不同风格簇**：

| 选项 | 策略 | 用户感知 |
|---|---|---|
| 1 最贴合 | 全局 top1 | 「就照这张图的感觉」 |
| 2 同题材异流派 | 同类但换风格簇（同为人物，一个暖调胶片一个冷调电影） | 「同一个题材，另一种拍法」 |
| 3 刻意偏移 | 相邻簇（暖→冷 / 全景→特写） | 「我想要不一样的感觉」 |
| 4 技术优先 | 只修缺陷不换风格 | 「不想改风格，只想变干净」 |

四者是**四种不同决策**，不是同一方案的四套措辞。这是「多个选项」和「同一个答案说四遍」的区别。

### 5.7 用户白话需求怎么进链路

需求有两种，处理方式不同：

| 类型 | 例子 | 处理 |
|---|---|---|
| **约束型** | 「我是男的」「要横图」 | 直接改硬过滤条件 |
| **偏移型** | 「再复古一点」「别那么亮」 | 解析成「目标维度 +N 档」，在检索时抬权，**不当关键词搜** |

偏移型必须走「维度偏移」而不是「文本检索」，因为「复古」在库里不是一个独立字段，它对应 `色调=暖` + `后期=颗粒/褪色` + `光线=柔光` 三个维度的组合。映射表约 20 条，写死在 L3。

## 6. 云函数够不够：量化判定

### 6.1 体积

| 项 | 实测 | 上限 | 占用 |
|---|---|---|---|
| L1 索引（列式 + 枚举 ID） | **181 KB**（gzip 26 KB） | 50 MB | 0.36% |
| L0 词表 | 34 KB | | 0.07% |
| L2 簇 + L3 规则 | ~15 KB | | — |
| **合计** | **~230 KB** | **50 MB** | **0.46%** |

对照：同样是这份数据，**行式 JSON 是 2140 KB**（键名重复 2253 次）。列式 + 枚举 ID 只有它的 **8%**，这是必须做的编码优化，不是可选优化。

### 6.2 运行时

| 项 | 估算 | 依据 |
|---|---|---|
| `JSON.parse(181 KB)` | 5-8 ms | Node 单线程解析中文 JSON 约 20-30 MB/s |
| 单次检索 | **3-6 ms** | 2253 × 33 = 74,349 次「数组取值 + 数值比较」 |
| 内存占用 | ~6 MB | 解析后对象 + 词表 |
| 响应体 | ~3 KB | 4 候选 × 200 字 |
| 端到端（快速模式） | 5-7 s | 1 次 vision 调用 |
| 端到端（增强模式） | 10-15 s | 2 次调用 |

对照上限：内存下限 128 MB（占 5%）、同步响应 6 MB（占 0.05%）、客户端 60 s（占 25%）。

**结论：云函数余量充足，没有任何一项接近上限。**

### 6.3 什么条件下才需要检索 server

四条触发条件，**任一满足**才考虑：

1. 条目 > **2 万**（JSON 超 1.5 MB，冷启动 +80-120 ms 开始有感）
2. 要上**向量语义检索**（云开发不支持 embedding + 向量索引，必须外挂）
3. 要**增量入库 / 人工标注后台 / AB 测权重**（需要写接口，云函数不适合做管理端）
4. 要给**小程序之外的端**复用（Web / H5 / 开放 API）

当前 2253 条，**四条一条都不满足** → 不建 server。

### 6.4 但必须接受三个代价

| 代价 | 说明 | 缓解 |
|---|---|---|
| **改数据要重新部署函数** | 不能热更 | 返回体带 `dataVersion`，前端可校验；部署已有脚本惯例 |
| **冷启动多 5-10 ms** | require 181 KB JSON | 可忽略；模块顶层 require，只解析一次 |
| **不能做标注后台** | 加条目要改代码重部署 | 条目量小时无所谓；>5000 条后再评估 |

## 7. 三个产品场景，一套数据

| | 场景 | 输入 | 输出 | 现有代码复用 |

## 8. 和现有 DeepSeek 分析的接法

### 8.1 现状

`promptAdvisor` 是「一次调用，模型自由发挥」：

```
图片 → [DeepSeek vision] → { analysis, candidates: [3 条改动描述] }
```

它**没有任何外部依据** —— 全靠模型自己的摄影知识。所以结果「看着像那么回事」，但和 2253 条经过人工标注的真实成片配方没有关系。

### 8.2 改造后

```
图片 → [DeepSeek vision] → 18 维标签 ─┐
                                      ├→ [本地检索] → top-8 / 4 簇
                                      │                    ↓
                                      └────────→ [few-shot 注入] → 4 候选
```

**检索结果不是答案，是给模型的「参考答案」。** 这是 few-shot 注入的本质：模型仍然要理解当前这张图，但它的表达被约束在「人类标注过的、真实成立的配方」附近。

### 8.3 具体改法（不动函数名、不动出参）

`promptAdvisor` 内部拆三段，用 `event.mode` 控制：

| mode | 行为 | 用途 |
|---|---|---|
| `labels` | 只跑 ①，返回标签 | 前端先渲染「AI 已识别」标签条，感知延迟减半 |
| `full`（默认） | ① ② ③ | 正常请求 |
| `reuse` + 传 labels | 跳过 ①，只跑 ② ③ | 用户点「换一批」时**零 vision 成本** |

出参形状保持 `{ ok, analysis, candidates: [{label, text}], model, elapsed }` 不变 →

**前端 `advisor.js`、缓存逻辑、`index.wxml` 全部不用改。** 这是这套方案能低成本落地的前提。

### 8.4 两次调用的取舍

| 模式 | 调用次数 | 延迟 | 成本 | 语言质量 | 建议 |
|---|---|---|---|---|---|
| 快速（槽位替换渲染） | **1** | 5-7 s | 1× | 机械拼接（但库本身就是这样） | **默认** |
| 增强（few-shot 生成） | 2 | 10-15 s | 2× | 自然流畅 | 用户点「让 AI 润色」才走 |

快速模式能成立，正是因为 §4 证明了「提示词可机械再生」。这条发现直接省掉一次模型调用。

## 10. 风险与验收

### 10.1 风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| vision 输出的标签不合法 | 检索失配、全 null | 已有 `extractJsonObject` 兜底 + **枚举白名单校验**，不在词表内的置 null 而非猜 |
| 标签错 → 检索偏 → 候选偏 | 用户觉得「这不是我想要的」 | 候选上显示**来源簇名**（可解释），用户能判断是「AI 看错了」还是「库里没有」 |
| **库偏置** | A 库 1450 条全是人像，风景/街拍只有 B 库 803 条 → 风景图结果全来自 B 库 | 硬过滤先按 `类别` 分桶，同桶内再排序 |
| 光线方向误标（§3.6） | 120 条底光误导排序 | 复核前降权 |
| 版权 | B 库来自米拍 / CNU / 太平洋 | 只用「风格描述文本」，不带原图、不带作者名；商用前需法务确认 |

### 10.2 验收标准（不写代码也能定义）

| 指标 | 目标 | 怎么测 |
|---|---|---|
| 检索准确率 | top1 簇与人工判断一致 ≥ **70%** | 人工挑 30 张跨题材图，标注期望簇，跑一遍对比 |
| 候选多样性 | 4 候选的簇重叠率 < **25%** | 统计 4 个候选的簇 id 重复数 |
| 延迟（快速模式） | p90 < **8 s** | 现有 `elapsed` 字段已在返回体里 |
| 单次成本 | < **¥0.005** | 按 token 用量算 |
| 回归 | 现有 3 条候选场景**不退化** | 同一批测试图，新旧方案各跑一遍人工对比 |
